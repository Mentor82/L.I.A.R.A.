## Overview

**LIARA** is a local AI-orchestration system with implemented governance and
validation paths. These paths are not equivalent to autonomous governance or
production readiness. Current capabilities include:
- Execution-backend-neutral ai-validator jobs with a real Docker Compose adapter
- Sys governance proposal/decision framework
- Async job execution model
- Persistent memory with graph-priority semantics
- Multi-provider inference routing with circuit breakers

This document is the **canonical system prompt** for development, testing, and deployment workflows.

## Validator: Self-Validation & Governance

### Two Execution Modes

**Mock Mode** (Development)
```bash
export LIARA_VALIDATOR_EXECUTION_MODE=mock
# Instant response, no Docker, for fast iteration
# Typical use: unit tests, quick smoke checks
```

**Worker Mode** (Production)
```bash
export LIARA_VALIDATOR_EXECUTION_MODE=worker
export LIARA_VALIDATOR_BACKEND=docker_compose
export LIARA_VALIDATOR_WORKER_ROOT=./workers/ai-validator
export LIARA_VALIDATOR_TIMEOUT_SECONDS=1800
# Real validation through the configured execution backend
# Typical use: CI/CD, live regression, deployment gates
```

The validator itself is not a Docker service contract. `docker_compose` is the
currently bundled `ValidatorExecutionBackend`; VM, remote-worker, and other
container adapters may implement the same typed request/result interface.

### Key Environment Variables

```bash
# Validator Execution
LIARA_VALIDATOR_EXECUTION_MODE=worker         # mock | worker (default: worker)
LIARA_VALIDATOR_BACKEND=docker_compose        # registered execution adapter
LIARA_VALIDATOR_ASYNC=1                       # 0=sync, 1=async (default: 1)
LIARA_VALIDATOR_WORKER_ROOT=./workers/ai-validator
LIARA_VALIDATOR_TIMEOUT_SECONDS=1800          # 30 minutes default

# Sys Governance
LIARA_SYS_GOVERNANCE_ENFORCE=0                # 1=enforce, 0=audit-only (default: 0)
LIARA_SYS_GOVERNANCE_STORE_PATH=./logs/services/sys_governance_proposals.json
LIARA_SYS_GOVERNANCE_EVENTS_PATH=./logs/services/sys_governance_events.jsonl

# Traceability
LIARA_AUDIT_ENABLED=1                         # Append-only sys audit trail
LIARA_SESSION_ID=<uuid>                       # Session context for audit
LIARA_RUN_ID=<uuid>                           # Run context for audit
```

## Sys Governance: Policy & Enforcement

### Governance Proposal Flow

1. **User invokes dangerous command** → `/tools/sys/invoke` with `command=rm|del|reboot|curl|wget`
2. **Policy evaluation** → Identifies risk tokens (rm/del/shutdown/reboot/format, network)
3. **Proposal creation** → `POST /tools/sys/governance/proposals` creates proposal with governance_id
4. **Approval required** → If `LIARA_SYS_GOVERNANCE_ENFORCE=1`, command is blocked until approved
5. **Decision submission** → `POST /tools/sys/governance/decisions` with `approved=true/false`
6. **Execution or rejection** → If approved, command runs; if rejected, returns error

### Governance Proposal Schema

```python
{
  "governance_id": "gov-uuid",
  "proposal_timestamp": "2026-07-13T16:30:00Z",
  "proposal_type": "sys_invoke",
  "command": "rm",
  "risk_tokens": ["rm"],
  "context": "user requested file deletion",
  "state": "pending",                  # pending | approved | rejected
  "decision": {
    "approved": true,
    "decision_timestamp": "2026-07-13T16:30:05Z",
    "approver": "human|system",
    "reason": "verified safe by user"
  }
}
```

### Policy Risk Assessment

```
BLOCKED_TOKENS = ["rm", "del", "rmdir", "shutdown", "reboot", "format", "fdisk"]
NETWORK_TOKENS = ["curl", "wget", "ssh", "telnet", "nc"]

if any(token in command for token in BLOCKED_TOKENS):
    proposal_type = "destructive"
    risk_level = "critical"
    enforce = LIARA_SYS_GOVERNANCE_ENFORCE

if any(token in command for token in NETWORK_TOKENS):
    proposal_type = "network"
    risk_level = "high"
    enforce = LIARA_SYS_GOVERNANCE_ENFORCE
```

### Audit Trail

**Governance Events (append-only JSONL)**
```bash

```

## Memory Service: Facts, Staging, Dreaming

### Fact Lifecycle

```
┌─────────────────────────────────────────────┐
│ Draft (ephemeral)                           │ ← Initial creation
├─────────────────────────────────────────────┤
│ Staged (candidate)                          │ ← Proposal-only
├─────────────────────────────────────────────┤
│ Verified (ground-truth)                     │ ← Human/trusted system gate
├─────────────────────────────────────────────┤
│ Deprecated (hidden but not deleted)         │ ← Graceful retirement
│ Revoked (explicit denial)                   │ ← Policy rejection
│ Deleted (cascade removal)                   │ ← System cleanup
└─────────────────────────────────────────────┘
```

### Staging & Consolidation

**Stage a Fact**
```bash
POST /staging/stage
{"fact": {"title": "...", "content": "..."}, "session_id": "sess-xxx"}
```

**List Staged**


## Decision Rules for AI Agents

### When Adding Code

1. **Validate before merge**: Run validator on all Python changes
   ```bash
   export LIARA_VALIDATOR_EXECUTION_MODE=mock  # dev
   POST /validator/submit {"workspace": "/path", "scope": "quick"}
   ```

2. **Check governance implications**: Flag any sys tool changes
   - Does this add new destructive commands?
   - Does it bypass governance gates?
   - Document risk tokens in comments

3. **Update audit trail**: If modifying memory/staging/dreaming:
   - Add traceability fields (session_id, run_id, request_id)
   - Emit append-only audit events via sys_audit hook
   - Test with persistence layer (not just in-memory)

4. **Persist & test**: For governance/memory changes:
   - Ensure JSON/JSONL writes are atomic (tmp → replace)
   - Test persistence over service restart
   - Verify audit events are queryable

### When Modifying Critical Services

| Service | Checklist |
|---------|-----------|
| **Validator** | [ ] Mock mode passes, [ ] Worker mode tested, [ ] Timeout handling verified |
| **Governance** | [ ] Proposals persist, [ ] Decisions immutable, [ ] Audit trail grows |
| **Memory** | [ ] Fact lifecycle honored, [ ] Graph priorities enforced, [ ] Staging consolidates |
| **API** | [ ] Traceability fields passed, [ ] Async jobs track state, [ ] Error responses clear |

### When Debugging

**Validator stuck?**
- Check `LIARA_VALIDATOR_EXECUTION_MODE` (should be "worker" or "mock")
- Check `LIARA_VALIDATOR_BACKEND` and whether that adapter is registered
- For `docker_compose`: verify the daemon and worker Compose file
- Check timeout: `echo $LIARA_VALIDATOR_TIMEOUT_SECONDS` (default 1800s)

**Governance not enforcing?**
- Check `LIARA_SYS_GOVERNANCE_ENFORCE` (must be "1" for prod)
- Check proposal file exists: `ls logs/services/sys_governance_proposals.json`
- Check events JSONL is growing: `tail -f logs/services/sys_governance_events.jsonl`

**Memory not persisting?**
- Check backend: `grep MEMORY_SERVICE_BACKEND .env` (default postgres)
- Check Postgres running: `docker compose ps | grep postgres`
- Check DB schema: `psql -U liara_user -d liara_db -c "\dt memory_*"`
