## 2026-07-13: Typisierter Workspace-Agent

Der bisherige einmalige Ablauf `Routing -> ein Toolcall -> Modelltext` wurde
fuer klar erkannte komplexe Workspace-Auftraege um einen begrenzten
Plan/Act/Observe-Pfad ergaenzt:

```text
komplexen Auftrag erkennen
-> typisierten Plan erzeugen
-> Schritt einzeln ueber sys ausfuehren
-> Mutation per Read-after-Write verifizieren
-> Zustand beobachten und Abhaengigkeit freigeben
-> abschliessend vorhandenen ai-validator ausfuehren
```

Pfadausbruch und Vorwaertsabhaengigkeiten werden vor der Ausfuehrung
abgewiesen. Schritt- und Ressourcenfreigaben entstehen aus `C(a)`, `U(a)`,
confidence-adjusted Utility, Entropie, RDS und actionable Risk. Das vorhandene
kalibrierte Threshold-Profil steuert Advisory, Soft-Control und Hard-Control;
starre 16-/3-/128-KiB-Laufzeitlimits wurden entfernt. Lediglich hohe
Parser-/Transport-Notkappen bleiben fail-closed. Der erste nicht erfolgreiche,
nicht verifizierte oder mathematisch nicht freigegebene Schritt stoppt die
Kette. Die Textual Runtime-Anzeige zeigt Agent-Schritte, Status und
Validatorzustand separat von den vorhandenen Chat-`turns`.

Die Budgetmathematik laeuft primaer ueber LIARAs vorhandene lokale Julia und
das neue allowlistete Modell `workspace_budget.jl`. Python bleibt als
auditierter Fallback erhalten. Workspace-/Testkommandos laufen davon getrennt
weiterhin im eingegrenzten Debian-WSL-Workspace.

Validator-Ergebnisse werden nun zusaetzlich als sessiongebundene
`workspace_agent_run`-Context-Artefakte persistiert. Folgefragen wie "Was
fehlte?" oder "Welche Validator-Findings gab es?" laden den neuesten Lauf und
geben konkrete Findings mit Datei, Zeile und Meldung deterministisch wieder.

## 2026-07-13: Native WSL-Session-Runtime

### Ziel

LIARA bleibt mit ihrem kanonischen Projekt unter `C:\ai\LIARA`. Tests,
Julia-Compute, Codeexperimente und veraendernde Simulationen erhalten einen
temporaeren nativen WSL-Arbeitsraum, ohne direkt in den kanonischen Projektroot
zurueckschreiben zu koennen.

### Implementiert

- Session-Lifecycle in `services/simulation/wsl_session_runtime.py`
- registriertes Lifecycle-Tool `wsl_session`
- Bindung registrierter Sessions an den bestehenden policy-gated
  `WslExecutorTool`
- direkte CLI unter `scripts/wsl_session_cli.py`
- gefilterte Snapshots mit harten Datei-, Gesamt- und Patchlimits
- read-only `source` und veraenderbares `work`
- Path-Confinement fuer Session-Root und Executor-Workdir
- Trace-Felder fuer Request, Run, Session und Source
- Collection mit Patch, Kandidat und SHA-256-Hashes
- vorbereiteter Handshake zum vorhandenen `ai-validator`
- append-only Session-Audit und lokale Registry
- Cleanup mit Beibehaltung lokaler Kandidaten-/Audit-Artefakte

-> /sys ls
-> /sys julia --version
-> verifizierte Mutation nur im Session-work

```

Der reale Lauf verwendete Debian WSL2 und Julia 1.12.6. Der Snapshot umfasste
855 Dateien und 7.071.941 Bytes. Die Testmutation erschien ausschliesslich im
exportierten Patch/Kandidaten; der kanonische LIARA-Root wurde dadurch nicht
veraendert.

- `tests/unit/test_wsl_session_runtime.py`

Governance  -> entscheidet ueber eine spaetere Uebernahme
```

## 2026-07-13: Textual-Frontend Write-Through-Haertung

### Befund

Der Workspace-Explorer unter `frontend/tex-ui` las den realen Debian-WSL-
Workspace korrekt, war aber nicht an die Chat-/Toolausfuehrung gebunden. Der
Chat-Payload enthielt keinen `sandbox_root`, `/sys` war im Frontend nicht
implementiert und Modelltexte wurden ohne Auswertung von `tool_outputs` oder
Write-Evidenz angezeigt.

### Umsetzung

- `sandbox_root` wird mit normalen Chat-Requests uebertragen.
- optionales `workspace_session_id` bindet direkte Befehle an eine registrierte
  WSL-Session.
- `/sys` verwendet strukturierte direkte Argumentlisten.
- `tee` transportiert Inhalt explizit als `stdin_text`, auch mehrzeilig.
- Tool-Metadaten bleiben im `ToolExecutionResult` bis zur API erhalten.
- `mkdir`, `touch` und `tee` erhalten einen realen Read-after-Write-Check.
- `tee` vergleicht den geschriebenen Inhalt beziehungsweise Append-Tail per
  SHA-256.
- nicht bestaetigte Dateisystembehauptungen des Modells werden in der UI
  sichtbar als unverified markiert.
- bei bestaetigten Writes nennt die UI nur den exakt nachgewiesenen Zielpfad;
  weitere Modellbehauptungen werden dadurch nicht implizit bestaetigt.
- `validation_passed=false` wird sichtbar als Validatorwarnung dargestellt.
- nach direkten bestaetigten Writes wird die aktive Workspace-Ansicht neu
  eingelesen.

### Verifikation

```text
192 passed
```

Zusaetzlich wurde der reale End-to-End-Pfad geprueft:

```text
frontend/tex-ui client
-> POST /tools/sys/invoke
-> WslExecutorTool
-> Debian WSL
-> mkdir + tee
-> Read-after-Write
-> mutation_verified=true
-> SHA-256-Evidenz
```

Der HTTP-Probelauf erzeugte eine Datei im eingegrenzten WSL-Probeverzeichnis,
las sie erfolgreich zurueck und entfernte das Probeverzeichnis anschliessend.

Der reale, persistierte Canary-Zustand deckte anschliessend einen
