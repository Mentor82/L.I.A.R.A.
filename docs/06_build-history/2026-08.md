# Build-Historie 2026-08

## 2026-08-10: Julia-Bridge auf kanonischen WSL-Pfad zurueckgefuehrt

Die interne `JuliaBridge` verwendete nach einer Konfigurationsdrift implizit
den lokalen Windows-Modus. Dadurch fiel der Orchestrator auf Python zurueck,
wenn der API-Prozess kein hostseitiges `julia` aufloesen konnte. Der Default
ist wieder `JULIA_BRIDGE_MODE=wsl`; `local` bleibt ein expliziter
Development-Override.

Der temporaere `/compute/run`-Smoke deaktiviert ausserdem die API-seitige
llama.cpp-Lebenszyklusverwaltung. Test-API-Instanzen koennen damit keinen
laufenden Inferenzprozess auf Port 8000 mehr ersetzen oder beim Shutdown
beenden.

Verifikation:

```text
tests/unit/test_simulation.py + tests/unit/test_api_app.py: 61 passed
Julia-Reasoning-Paritaet inklusive natuerlicher Chat-Mathematik: 5 passed
Julia SYS smoke: success
POST /compute/run: HTTP 200, turbine_power = 31.4159 kW
llama.cpp Prozess-IDs vor/nach temporaerem API-Smoke identisch
```

Der anschliessende Live-Chat-Canary zeigte eine zweite, getrennte Luecke:
`route_reason=sys_julia` war korrekt, aber `chat_math.jl` verstand nur
symbolische Operatoren. Die allowlistete Grammatik normalisiert nun auch eng
begrenzte deutsche und englische Operatorwoerter wie `mal`, `plus`, `minus`
und `geteilt durch`, bevor die bestehende strikte Zeichenpruefung greift.

Live-Abschluss:

```text

Anfrage: Berechne 17 mal 23 und antworte kurz mit dem Ergebnis.
Antwort: Das Ergebnis von 17 x 23 ist 391.
reasoning_metrics.compute_backend: julia
reasoning_metrics.compute_path: primary
reasoning_metrics.fallback_reason: null
```
